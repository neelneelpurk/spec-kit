# Security Policy

## Reporting a Vulnerability

Please report suspected vulnerabilities through GitHub private vulnerability
reporting:

<https://github.com/neelneelpurk/infrakit/security/advisories/new>

Do not open a public issue, public discussion, or public pull request for a
security vulnerability before the maintainers have had time to investigate and
release a fix.

Include as much of the following as you can:

- Affected version, commit, or release asset (`infrakit version` output).
- Reproduction steps or proof-of-concept details.
- Expected and observed impact.
- Relevant logs, terminal output, or screenshots with secrets removed.
- Whether the issue is already being exploited or publicly discussed.

Maintainers will acknowledge a valid private report within three business days
when possible, triage severity, and coordinate disclosure through the GitHub
security advisory. If a fix is needed, it will be released before public
disclosure unless there is an active exploitation risk that requires faster
notice.

## Supported Versions

Security fixes target the current stable major release unless a separate support
window is announced in release notes.

| Version | Supported |
| ------- | --------- |
| 1.x     | Yes       |
| < 1.0   | No        |

## Scope

InfraKit is a Python CLI that scaffolds a project from templates bundled inside
the published wheel. `infrakit init` runs **entirely offline** — there are no
network calls during init, check, mcp, or version. Security reports are in scope
when they affect the confidentiality, integrity, or availability of InfraKit
itself in normal supported use, including:

- The published `infrakit-cli` wheel and its release/publish path on PyPI.
- The CLI's filesystem behavior during `init` (path handling, the files it
  writes, and where it writes them).
- The prompt, persona, and asset **templates** shipped in the wheel — for
  example a prompt-injection or unsafe-default issue in a template that InfraKit
  renders into a user's project.
- Secrets handling in the CLI's own configuration and generated `.infrakit/`
  artifacts.

The following are **out of scope** for this project and should be reported to the
relevant upstream:

- Vulnerabilities in the AI coding agents InfraKit targets (Claude Code, Codex,
  Gemini CLI, Copilot) or in the IaC tools (Terraform, Crossplane, AWS CLI).
- The security posture of infrastructure **generated by** the AI agent. InfraKit
  encodes secure-default guidance into its personas, but the generated `.tf` /
  YAML / CloudFormation is the user's responsibility to review before `apply`.
  The security-review persona is a heuristic first-pass guardrail, not a
  substitute for a human audit.
- Expected behavior in trusted local development environments and documented
  administrative actions.

## Release Integrity

Releases are built and published from `pyproject.toml` by GitHub Actions
(`.github/workflows/release.yml`) on merge to `main`. The CLI is distributed
through PyPI and tagged GitHub Releases. Pin a specific version
(`uv tool install infrakit-cli==X.Y.Z`) and verify it against the
[PyPI release history](https://pypi.org/project/infrakit-cli/#history) when you
need a reproducible install.
